## 表情面板首开慢的定位与优化

- 瓶颈不在 emoji-mart 初始化：缓存命中后 100ms 内面板就完整（170 个按钮、搜索框、分类齐全），无 >50ms 长任务；CPU 4x 节流也只多几十毫秒。
- 真正原因：`React.lazy` 让 554K 的 async chunk（`6774.*.js`，内含 424K `@emoji-mart/data/sets/15/native.json`，3395 个 emoji）**首次点击才下载**。本地静态服务未开 gzip，传的是 554K 原文（gzip 后仅 111K）；Fast 3G（1.6Mbps/150ms RTT）实测首次点击到面板完整 **2997ms**，其中 chunk 下载占 2974ms。
- 优化：`EmojiButton.tsx` 把 `loadPicker()` 的 Promise 提到模块级缓存，`React.lazy` 与预取共用；`useEffect` 里用 `requestIdleCallback`（fallback `setTimeout 1500`）在首屏空闲期预取，按钮 `onPointerEnter` / `onFocus` 再兜一次；Promise reject 时清缓存以便重试。首屏不受影响，慢网首次点击降到 **41ms**。
- 部署侧仍需给 `.js/.css` 开 gzip/brotli（554K → 111K），否则预取阶段仍会占 554K 带宽；Nginx 需 `gzip_types application/javascript text/css;`（默认只压 text/html）。
- 备选未实施：关闭时不卸载面板、改用 `visibility:hidden` 保持挂载，可省掉每次 `new Picker()` 重建（本地重复打开仅 ~100ms，收益有限且会带来隐藏态布局/焦点风险）。

## 关闭表情面板的打开动画

- 项目 `.panel` 自身没有动画；动画全部来自 emoji-mart shadow DOM 内的 `--duration: 225ms` / `--duration-fast: 125ms` / `--duration-instant: 50ms`（分类导航条滑动、搜索框、表情按钮背景、肤色菜单）。库没有 `@keyframes`，只有 transition；仅在 `prefers-reduced-motion` 下才把这些变量置 0。
- 关键坑：这些变量声明在 shadow DOM 内部的 `#root` 规则里，元素自身声明优先于继承，因此从外部 `.panel` / `em-emoji-picker` 设 `--duration: 0`（加 `!important` 也不行）**无效**；`::part` 也未暴露。只能往 `shadowRoot` 注入 `<style>`。
- 实现：`EmojiButton.tsx` 模块级常量 `NO_MOTION_CSS`（把三个变量设 0ms + `*,*::before,*::after { transition:none!important; animation:none!important }`），打开时用 `useEffect` 查找 `em-emoji-picker.shadowRoot` 注入带 `data-no-motion` 标记的 style；因 Picker 是懒加载自定义元素、shadowRoot 可能晚几帧，用 `requestAnimationFrame` 最多重试 30 帧并去重。
- 验证（CDP 读 computed style）：`--duration/-fast/-instant` 全为 `0ms`，nav bar / 搜索框 / 表情按钮 / 外层浮层 `transitionDuration` 均为 `0s`、`animationName` 为 `none`；关闭再打开会重新注入；插入 👍、面板 170 个按钮、布局均正常，无报错。

## 修掉表情面板真正的「展开动画」（尺寸自激循环）

- 用户看到的丑陋展开不是 CSS 动画，而是**面板高度每帧 +2px、从 322 涨到 424，top 从 110 一路升到 8，持续约 900ms**（CDP 逐帧录 `getBoundingClientRect` 确认）。
- 根因：`anchored.ts` 的 maxHeight 分支用 `floating.scrollHeight + 2` 当作内容高度，再把结果写成浮层 inline height；而表情面板内容用 `height:100%` 跟随父，于是 `scrollHeight` 随写入高度一起增长，ResizeObserver 再次触发 update → `height_{n+1} = height_n + 2` 的自激循环，直到被 `min(maxHeight, available)` 截断。`Select` 也用该分支但内容不跟随父高度，无此问题。
- 修复：`AnchoredOptions` 新增 `contentHeight?: number`，给定时用固定值替代 `floating.scrollHeight + 2`（默认行为不变，不影响其它调用方）；`EmojiButton` 传 `contentHeight: 435`；`.loading` 占位 width 320→300、`min-height:320px`→0，与 Picker 同尺寸，消除首帧宽度跳变。
- 复测：从第 1 帧起 `top=8 / width=300 / height=424` 全程恒定（900ms 内只变按钮数 -1→90→170，属内容渲染）；关闭再打开尺寸一致；动画变量仍 0ms；插入 👍 正常；无报错。

## 附件上传限制对齐官方（同日晚）

- 用户给官方上传按钮 tooltip 截图（「最多 20 个，每个 100 MB」），要求附件限制为**单个 100MB / 最多 20 个**。原 `src/services/attachments.ts`：`MAX_SIZE_MB=64`（注释称与 Files API 一致）、`MAX_USER_DATA_SIZE_MB=32`（纯文本/代码/表格/电子书按 user_data 上传时更小）、`MAX_COUNT=50`；`DragMask.tsx` 用常量显示「最多 50 个，每个 64MB」，与官方不符，且提示 64MB 但文本类实际只放行 32MB，属既存的文案/行为不一致。
- 改为 `MAX_SIZE_MB=100`、`MAX_COUNT=20`，删除 `MAX_USER_DATA_SIZE_MB` 与 `getMaxSizeMB()`，`validateFiles` 统一按 100MB 校验（不再按 purpose 区分）。`getUploadPurpose` 保留：上传时仍要把 purpose 传给 Files API，只是不再参与体积校验。
- i18n zh：`dragFileDesc` / `uploadMaxMBSize` 的 `{size}MB` → `{size} MB`（与截图及 en 一致）；数字全部由常量注入，无硬编码。
- 风险：64/32 原注释写的是 Files API 侧上限，放宽到 100MB 后若服务端仍只收 64/32，超限文件会在上传阶段失败并显示「上传失败」；要保守可恢复 purpose 细分（把按文件类型返回 32/64 的逻辑加回 `validateFiles`）。
- 验证：type / lint(125 规则 0 错误) / 14 例测试 / build 全过且 0 warning；CDP 回归：拖拽遮罩显示「最多 20 个，每个 100 MB」、拖入 21 个文件提示「上传文件最多支持 20 个」、伪造 101MB 文件提示「单个文件大小超过限制（100 MB），请调整后重试」、0 控制台错误。
